# Sikka Queue Analytics

موقع مستقل يجمع ويحلل انتظار كل لعبة في الحديقة 335. الهدف تزويد سكة لاحقًا ببيانات تساعد في ترتيب الألعاب: المتوسط، ساعات الهدوء والذروة، متى يرتفع الانتظار، ومقارنة التاريخ ويوم الأسبوع. لا يعدّل مستودع SIKKA ولا يحتاج حسابات زوار أو AI.

## ما الذي يعمل

- Spring Boot 3.5.16 / Java 17 / MySQL 8 مع Flyway، وواجهة React 19 / Vite بالعربية والإنجليزية.
- خدمة جمع على الخادم، تبدأ عند تشغيل التطبيق ثم تحفظ دورة كل 5 دقائق حتى دون فتح الموقع.
- قفل قاعدة بيانات داخل معاملة يغطي دورة الجمع، مع قيود فريدة للدورة ولعبة/فترة. النسخ المتزامنة لا تحفظ قراءات مكررة. أي فشل كتابة يلغي المعاملة كاملة ويظهر في سجل الخادم ويعاد في الدقيقة التالية؛ فشل المصدر يحفظ CollectionRun FAILED.
- طلب واحد للحديقة، مع 3 محاولات إجمالًا عند الأخطاء المؤقتة وتأخير 1 ثم 2 ثانية ومهلة 12 ثانية للطلب. 4xx غير 429 لا يعاد.
- مصدران داخل الاستجابة: `lands[].rides[]` و`rides[]`، وإزالة التكرار بـsourceRideId. الاسم ليس مفتاح الهوية.
- Dashboard، بحث وتصفية، تحليل كل لعبة، خط انتظار مع فجوات، ساعات يومية، مصفوفة أيام الأسبوع، مقارنة التواريخ، مراقبة الجمع، CSV وواجهات قراءة لسكة.

## قواعد التحليل المعتمدة

نستخدم البيانات المتاحة، حتى لو يومًا أو يومين أو ساعة بها قراءة واحدة. لا يوجد شرط انتظار 3 أيام لتوليد توصية. كل نتيجة تعرض عدد القراءات والأيام؛ الثقة LOW مبدئية، MEDIUM من 3 أيام، HIGH من 7 أيام، وتبقى LOW إذا كانت ساعة من الساعات الداعمة قليلة القراءات. اليوم الجاري يدخل المقارنة ويظل مبدئيًا.

- UTC للتخزين. حدود الأيام والساعات في `Asia/Riyadh`.
- المتوسط اليومي: متوسط القراءات الصحيحة الحديثة وقت جمعها عندما تكون اللعبة مفتوحة. المفتوح بصفر صالح؛ المغلق أو القديم أو غير الصحيح مستبعد. القيم المفقودة والسالبة لا تتحول إلى صفر.
- التاريخ: نحسب متوسط الساعة لكل يوم أولًا، ثم متوسط هذه القيم بأوزان متساوية للأيام. لا يطغى يوم به قراءات أكثر على يوم آخر.
- زيادة الوقت: ارتفاع متوسط الساعة 10 دقائق أو أكثر عن السابقة، مع بيان عدد الأيام المتاحة؛ مقارنة وصفية وليست استنتاجًا سببيًا أو توقعًا مضمونًا.
- الساعات بعد الفتح: من انتقال مرصود لكل لعبة من إغلاق حديث إلى فتح حديث خلال 15 دقيقة. هذا **ليس موعد فتح الحديقة الرسمي**. لا نحسب أول قراءة وقت فتح ولا نستخدم يومًا لم يُرصد فيه الانتقال. قد يكون الانتقال إعادة فتح خلال اليوم؛ يجب تثبيت ساعات الحديقة الرسمية قبل وصف النتيجة بأنها «بعد أول ساعتين من فتح الحديقة».
- ترشيح الخطة: نفس يوم الأسبوع عند توفر يومين مماثلين، وإلا كل الأيام المتاحة. أفضل وأسوأ ساعة داخل نطاق الوصول والمدة. عند عدم وجود تاريخ صالح تعرض الواجهة عدم التوفر؛ الانتظار الحالي صالح فقط إذا كان حديثًا ومفتوحًا.
- الثقة LOW/MEDIUM/HIGH تصنيف وصفي لكفاية البيانات وليس احتمالًا إحصائيًا معايرًا. `p75DailyMean` هو المئين 75 لمتوسطات الأيام، وليس لزمن الانتظار الفعلي للزائر.
- قدم المصدر يُحفظ وفق وقت تحديثه مقارنة بوقت الجمع، وحده الافتراضي 15 دقيقة قابل للضبط. آخر قراءة تتحقق من قدمها مجددًا وقت الطلب؛ البيانات التاريخية لا تُستبعد لمجرد مرور أيام على حفظها.
- التغطية = القراءات المقبولة / الفترات المتوقعة؛ وهي تغطية انتظار صالح وليست نسبة فتح الحديقة. مراقبة الجمع تعرض تغطية دورات الجمع منفصلة، والفشل والفجوات منفصلين. يوم التشغيل الأول يشمل ساعات ما قبل التشغيل كتغطية ناقصة.

التاريخ يبدأ من أول تشغيل ناجح فقط. مصدر القراءات الحية لا يعيد تاريخًا ماضيًا تلقائيًا. لا بيانات تجريبية ولا أصفار مصطنعة في الإنتاج.

## التشغيل المحلي

```bash
cp .env.example .env
# غيّر كلمات مرور MySQL في .env
# Docker وDocker Compose مطلوبان

docker compose up --build -d
```

افتح http://localhost:8080. نفس الخدمة تقدم الواجهة وAPI. MySQL محفوظة في volume باسم queue_data. Flyway يشغّل الترحيلات تلقائيًا وHibernate يستخدم validate، ولا توجد إعادة إنشاء تدميرية للجداول.

للتطوير، شغّل MySQL ثم backend مع متغيرات DATABASE_URL/USERNAME/PASSWORD، ثم:

```bash
cd backend
./mvnw spring-boot:run
# في طرفية أخرى داخل frontend:
npm ci
npm run dev
```

Vite يمرّر /api إلى localhost:8080. MySQL JDBC URL يجب أن يبدأ بـ`jdbc:mysql://`؛ MYSQL_URL الخاص بـRailway ليس JDBC URL كما هو.

## النشر على Railway

1. مشروع مستقل مع خدمة MySQL ذات volume وخدمة GitHub من هذا المستودع، فرع main، root directory `/`، Dockerfile الموجود. ملف railway.json يضبط healthcheck وإعادة التشغيل ونسخة واحدة.
2. ضع متغيرات خدمة التطبيق التالية باستخدام reference variables إلى خدمة MySQL (اسمها في هذا المثال MySQL):

```text
DATABASE_URL=jdbc:mysql://${{MySQL.MYSQLHOST}}:${{MySQL.MYSQLPORT}}/${{MySQL.MYSQLDATABASE}}?connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true
DATABASE_USERNAME=${{MySQL.MYSQLUSER}}
DATABASE_PASSWORD=${{MySQL.MYSQLPASSWORD}}
COLLECTOR_ENABLED=true
```

3. فعّل domain لخدمة التطبيق على المنفذ الذي يوفره PORT (الافتراضي 8080). لا تفعّل serverless/sleep؛ الجمع يحتاج خدمة تعمل دائمًا.
4. افحص `/actuator/health` ثم `/api/v1/collector/status`. تحقق من 3 دورات حقيقية متتالية بفارق 5 دقائق دون فتح الواجهة، ومن بقاء عدد السجلات بعد إعادة تشغيل التطبيق. سجل `firstReadingAt` و`totalSnapshots` من API؛ لا تعتبر GitHub push دليل بدء الجمع.
5. لا حاجة لتطبيق frontend منفصل أو CORS في نشر الخدمة الواحدة. إذا فُصلت الواجهة، اضبط VITE_API_BASE عند بنائها وCORS_ORIGINS في الخادم بقائمة أصول مفصولة بفواصل.

## إعدادات البيئة

| المتغير | الافتراضي / المعنى |
|---|---|
| DATABASE_URL | JDBC MySQL URL، مطلوب للإنتاج |
| DATABASE_USERNAME / DATABASE_PASSWORD | من مرجع خدمة قاعدة البيانات، لا تحفظ في Git |
| PORT | 8080 أو المنفذ الذي تحدده المنصة |
| SOURCE_URL | https://queue-times.com/parks/335/queue_times.json |
| PARK_ID | 335 |
| COLLECTION_INTERVAL_MINUTES | 5، بين 5 و60، يخزن الفترات على حدود UTC |
| STALE_MINUTES | 15 |
| LOW_COVERAGE_SAMPLES | 6، علامة تغطية منخفضة لا تمنع الاستفادة من قراءات أقل |
| DISPLAY_TIMEZONE | Asia/Riyadh |
| COLLECTOR_ENABLED | true؛ false لتعطيل الجمع في اختبار أو بيئة ثانوية |
| CORS_ORIGINS | فارغ؛ الواجهة وAPI بنفس الأصل |

شغّل نسخة واحدة من التطبيق افتراضيًا. قفل DB يحمي التوسع أو تداخل إعادة النشر طالما تتشارك النسخ قاعدة البيانات نفسها. تغيير فترة الجمع بعد بدء التاريخ يغيّر معنى التغطية؛ أبقها 5 دقائق للتاريخ المتجانس.

## API لسكة

كل المسارات GET وقراءة فقط، ومعرّف اللعبة هو `sourceRideId` الخارجي. لا توجد endpoints عامة لتعديل الجدولة أو البيانات.

| المسار | الاستخدام |
|---|---|
| /api/v1/rides | قائمة الألعاب، أحدث قراءة، متوسط اليوم وعددها والتغطية |
| /api/v1/rides/{id}/latest | وقت المصدر والجمع والحالة والقدم وusableForPlanning |
| /api/v1/rides/{id}/daily?date=YYYY-MM-DD | متوسط اليوم والذروة والهدوء و24 ساعة وخط القراءات |
| /api/v1/rides/{id}/hourly?date=YYYY-MM-DD | المتوسط وعدد القراءات والتغطية لكل ساعة؛ لا بيانات = null |
| /api/v1/rides/{id}/patterns?from=YYYY-MM-DD&to=YYYY-MM-DD | كل الأيام وأيام الأسبوع والتواريخ والارتفاع وبعد الفتح؛ حتى 90 يومًا شاملًا |
| /api/v1/rides/{id}/planning-insights?date=YYYY-MM-DD&arrivalHour=12&durationHours=8 | ساعات مرشحة حسب البيانات المتاحة خلال آخر 60 يومًا واليوم الجاري، مع الثقة ومصدر المقارنة |
| /api/v1/collector/status | آخر نجاح وخطأ، أول قراءة، العد الإجمالي وسجل آخر 100 دورة |
| /api/v1/export/snapshots?from=YYYY-MM-DD&to=YYYY-MM-DD&sourceRideId=16289 | CSV حتى 31 يومًا؛ sourceRideId اختياري |
| /actuator/health | صحة الخادم وقاعدة البيانات |

عدد أيام الأنماط يعني أيامًا رُصدت فيها بيانات، وليس بالضرورة أيام تغطية كاملة. يجب على سكة فحص `confidence`, `daysCount`, `sampleCount`, `usableForPlanning`، ثم إضافة قيود الأهلية والمشي والصلاة والتجمع. هذه الخدمة لا تنشئ جدول زيارة كاملًا.

## الاختبارات

```bash
cd frontend && npm ci && npm run build
cd ../backend && ./mvnw verify
```

JUnit لقواعد المتوسطات والقراءات غير الصالحة واليوم المحلي والفجوات وأوزان الأيام. اختبارات تكامل H2 للترحيلات وJPA والقفل ومنع التكرار والتراجع الذري والفشل والتوصية من يومين. نفس عقد اختبارات DB يُشغّل أيضًا على MySQL 8.4 في GitHub Actions؛ لتشغيله محليًا اضبط TEST_MYSQL_URL وTEST_MYSQL_USERNAME وTEST_MYSQL_PASSWORD لقاعدة **اختبار منفصلة**. الاختبارات تمسح جداول الاختبار في بداية كل حالة.

## النسخ الاحتياطية والاستعادة

فعّل backups لقرص MySQL من إعدادات المنصة، وحدد جدولًا واحتفاظًا يناسب الاستخدام. لا تحذف volume أثناء التحديث. خذ أيضًا نسخة منطقية دورية واحفظها خارج الخادم:

```bash
# يطلب كلمة المرور تفاعليًا؛ لا تضعها في سجل الأوامر
mysqldump -h DB_HOST -P DB_PORT -u DB_USER -p --single-transaction --no-tablespaces --set-gtid-purged=OFF queue_analytics > queue-backup.sql
# استعد إلى قاعدة جديدة أولًا، مع إيقاف الجمع في التطبيق المستهدف
mysql -h DB_HOST -P DB_PORT -u DB_USER -p restored_queue_analytics < queue-backup.sql
```

اختبر الاستعادة وعدّ السجلات وصحة أول وآخر قراءة قبل تحويل التطبيق إليها. احتفظ بجدول flyway_schema_history ضمن النسخة. لا ترفع ملفات النسخ الاحتياطية أو بيانات الاتصال إلى GitHub.

## إسناد المصدر

[Powered by Queue-Times.com](https://queue-times.com/) ظاهر في الواجهة. [تعليمات API](https://queue-times.com/pages/api) تذكر تحديثًا كل 5 دقائق وأوقات مصدر UTC. البيانات انتظار معلن وليست قياسًا لوقت كل زائر فعليًا.

## نافذة الجمع الاختيارية

`COLLECTION_WINDOW_ENABLED=true`, `COLLECTION_START_HOUR=16`, `COLLECTION_END_HOUR=24` تقصر الجمع والتحليل المقبول وحساب التغطية على 16:00 حتى ما قبل 00:00 بتوقيت DISPLAY_TIMEZONE. هذه نافذة تشغيل يحددها المشغل وليست ساعات رسمية مؤكدة للحديقة. التاريخ القديم محفوظ؛ القراءات خارج النافذة لا تدخل متوسطات التحليل عند تفعيلها.

عند تفعيل Railway Serverless يلزم مؤقت خارجي لإيقاظ خدمة التطبيق في فترة الجمع. المهمة المرافقة تطلب health كل 5 دقائق من 13:00 إلى 20:59 UTC (16:00–23:59 الرياض). يضبط Hikari minimumIdle=0 وidleTimeout=60000 وkeepaliveTime=0 للسماح بخمول الشبكة خارج الفترة. لا تنم قاعدة MySQL. النوم ليس فوريًا عند منتصف الليل ولا يوفر تكلفة قاعدة البيانات؛ زيارات المستخدمين قد تبقي التطبيق مستيقظًا.
